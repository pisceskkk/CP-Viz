CPvLLM PCP & DCP

CONTEXT PARALLEL / 01

让长上下文协同计算

PCP 分配本轮 token 的工作，DCP 分担 KV 序列的存储与读取。

  • 主线：普通 GQA attention
  • 代码快照：2026-10-22
  • 点击任意图块或箭头，查看固定版本源码
Ascend · ModelRunnerV2 · GQA01 / 13
讲解备注

今天先回答两件事：谁负责本轮 token 的计算，谁负责保存和读取 KV。我们沿 Ascend ModelRunnerV2 的普通 GQA 路径展开。图里的 rank 是通信组中的参与进程；张量形状省略 batch 与部分模型维度。PCP、DCP 的名称来自各自主要目标，但执行时也需要处理另一阶段。

建立直觉 / 02

切分工作，保留可见范围

对位置 t 的 query，最终结果仍要覆盖该请求从开头到 t 的全部可见 KV。

  • Q 决定要算哪个位置
  • K/V 提供该位置能看到的上下文
  • 并行后，完整可见范围由所有参与者共同覆盖
Ascend · ModelRunnerV2 · GQA02 / 13
讲解备注

以标准因果 GQA 为例，当前位置也参与 attention。PCP 从 query 的工作分工入手；DCP 从 KV 的保存和读取分工入手。图展示的是一个 query/head 的语义，GQA 的多个 query heads 可以共享 KV heads。

框架视角 / 03

一份逻辑批次，两种执行视图

ModelRunnerV2 维护全局请求语义，并将计算组织成各 rank 的本地布局。

  • 全局位置：模型看到 token 的原始位置
  • 本地布局：设备只执行分配给它的工作
  • 出口顺序：结果重新对应正确请求
Ascend · ModelRunnerV2 · GQA03 / 13
讲解备注

框架的关键职责是保存全局到局部、局部到全局的对应关系。Padding 用于满足执行形状，但不应进入有效 KV 或采样结果。图回放也必须保持当前批次的有效长度、位置与映射正确。恢复的是采样所需的隐藏状态与批次对应关系，不要求各 rank 生成一份独立且不同的采样。

PCP / 04

首尾配对，平衡因果工作量

较晚的 query 能看到更多 KV；把前段与后段搭配，能让两个 rank 的工作更接近。

  • 示例：PCP=2，DCP=1；单请求、无历史前缀
  • 每段 2 token：有效因果配对数依次为 3、7、11、15
  • 实际耗时还受长度、padding、内核与通信影响
示例：PCP=2 · DCP=1 · 8 tokens04 / 13
讲解备注

token 0 至 7 分别能看到 1 至 8 个 key，因此四段的配对数是 1+2、3+4、5+6、7+8。首尾配对后两边都是 18。这里统计的是稠密因果 attention 的有效配对数，不是实测内核运行时间。当前 chunk 的分段、历史前缀、短请求以及组合 DCP 配置会影响实际布局。

PCP / 05

Q 保持本地，KV 通过通信补齐

每个 rank 计算自己的 query；所需 KV 通过交换、缓存位置与索引获得正确的逻辑可见性。

  • 形状示例：N=8；Hq / Hkv 为本地头数，d 为头维度
  • 通信缓冲区可按 rank 拼接，逻辑顺序由元数据表达
  • 模型出口再恢复 token 顺序
示例：PCP=2 · DCP=1 · GQA05 / 13
讲解备注

延续上一页 PCP=2、DCP=1 的例子。每个 rank 投影并处理自己负责的四个 token。KV gather 的物理排列可以是 rank 拼接顺序；缓存 slot 或后续索引负责让 query 看见正确的逻辑 token。Q 保持本地这一描述针对本页 PCP 单独开启的路径。结合 DCP 的历史 attention 路径还可能传输 Q，后面会展开。

缓存视角 / 06

通信得到的 KV，要按归属保存

本轮计算如何交换 KV，与缓存按什么归属保存 KV，是两项需要配合的职责。

  • PCP 的主要收益来自计算分工
  • DCP 提供 KV 序列的分片存储与并行读取
  • 图中两个出口代表不同配置
Ascend · ModelRunnerV2 · GQA06 / 13
讲解备注

在普通 GQA 路径中，单独开启 PCP 会将各 owner 生成的当前 KV 交换回来，保留同一 TP 头范围上的完整序列副本。DCP 通过缓存映射决定本 rank 负责哪些 KV token。KV 写入可以发生在 attention 读取之前；分片描述的是所有权与可见区间，不是强制的先算后存时序。

DCP / 07

同一个 query，读取不同 KV 分片

每个 rank 计算同一 query/head 在自己 KV 子集上的贡献，再合成完整输出。

  • 示例：PCP=1，TP=2，DCP=2；两个 rank 复用 TP 资源
  • KV 子集覆盖完整可见范围，各 token 只贡献一次
  • 图中展示普通单 token decode 的完整 KV 路径
示例：PCP=1 · TP=2 · DCP=207 / 13
讲解备注

DCP=2 在本例复用 TP 的两个 ranks。跨 rank 传递的是计算需要的 query heads，而不是必然广播所有模型 heads。各 rank 的 KV 子集通常按配置的交错粒度分布，图示不承诺连续前半段、后半段。普通单 token decode 可用一次本地 attention 读取含当前位置的本地 KV；多 query 或投机场景也可能采用历史与当前拆分路径。

DCP / 08

用 LSE 找回正确权重

局部输出已经各自归一化；合并时还要恢复每个 KV 子集在全局分母中的份额。

L = log ∑ᵢ exp(LSEᵢ)　　O = ∑ᵢ exp(LSEᵢ − L) · Oᵢ

  • 同一 query/head、相同打分尺度与可见性规则
  • KV 子集互不重叠，并覆盖目标可见范围
  • 空分片：O=0，LSE=−∞；与有效分支合并时权重为 0
Ascend · ModelRunnerV2 · GQA08 / 13
讲解备注

LSE 是当前 query/head 在该 KV 子集上的 softmax 分母的对数。O_i 是局部已归一化输出。数值例子使用标量输出帮助理解；真实输出是向量。实现用数值稳定的方式处理指数。全部历史分片为空时，需与有效当前分支一起处理，不能直接对全为负无穷的集合做未保护的归一化。

历史与当前 / 09

两段上下文，合成一次完整 attention

Chunked prefill 的 query 同时读取历史前缀和当前 chunk 的因果可见部分。

  • H：此前已处理的 token 数；C：本轮 chunk 的 token 数
  • 参与合并的历史与当前逻辑区间互不重叠
  • 对同一输出 query/head，当前区间贡献只计一次
Ascend · ModelRunnerV2 · GQA09 / 13
讲解备注

历史 token 均早于当前 chunk 的 query，因此历史分支读取其完整历史子集；当前分支保留因果掩码。这条区间规则约束计算贡献，而不是物理 cache 是否已经存有当前 KV。当前分支可以在不同 rank 上为各自负责的 query/head 计算，关键是在同一最终输出的归约中仅计一次。

PCP 的另一阶段 / 10

Decode 可以按请求分配 owner

在 PCP>1、DCP=1 的 Ascend 路径中，每步按请求分工，再汇集 KV 并恢复结果顺序。

  • owner 由本步的 decode 请求顺序决定，可以随步骤改变
  • KV 副本与结果恢复支持下一步重新分配
  • 叠加 DCP 时，参与者需要共同访问分片 KV
适用范围：PCP>1 · DCP=110 / 13
讲解备注

此页明确限定 PCP>1、DCP=1。框架按本轮有效 decode 请求的序号轮转分配 owner，无需永久绑定 rank。示例为普通单 token decode，实际策略同样覆盖投机解码的多 token 验证。一旦同时开启 DCP，同一请求的 query 需分发到各 KV 分片参与者上协同计算。

组合模式 / 11

历史分片需要看到对应的全部 Q

PCP+DCP 的 prefill 历史路径先补齐 query，再计算各 KV 分片，最后取回本地 query 的结果。

  • 本地 Q 的工作归属与历史 KV 的保存归属需要同时对齐
  • query 的额外通信服务于历史分片计算
  • 最终输出仍对应本 rank 的本地 query
Ascend · ModelRunnerV2 · GQA11 / 13
讲解备注

这一页避免把 PCP 单独开启时的 Q 留本地泛化。组合模式中，历史分支先在 PCP token 维汇集 query 并恢复逻辑排列，然后按需要补齐独立的 query heads。各 KV 分片算完后交换部分结果，再选择本地 query 对应的历史贡献，并与当前因果分支合并。

配置视角 / 12

DCP 在已有参与者之间组织分片

在这个代码版本中，PCP 启用后，DCP 可覆盖 PCP 轴，或覆盖整个 TP×PCP 域。

  • PCP=1 时：DCP 复用 TP ranks，DCP 大小需整除 TP
  • DCP 的大小描述分片协作组，不额外乘一套独立设备
  • 合法的组大小仍需满足具体模型、后端与运行模式约束
Ascend · ModelRunnerV2 · GQA12 / 13
讲解备注

将 PCP 与 DCP 理解成两项分工，而不是两个必然正交、设备数直接相乘的维度。本页的组大小约束来自固定版本配置校验；实际拓扑构造先跨 PCP 再跨 TP。组大小满足这里的规则，只是配置条件之一，不代表所有模型、KV 格式和后端都支持相同组合。

回到工程 / 13

沿着三条线，读懂上下文并行

追踪 query 的工作归属、KV 的保存归属，以及输出的归一化与顺序，就能理解整条路径。

  • 收益：更多计算与 KV 访问可以并行进行
  • 代价：KV / Q / 输出通信，以及负载与 padding 开销
  • 选型依据：真实长度分布、并发、内存和端到端测量
Ascend · ModelRunnerV2 · GQA13 / 13
讲解备注

性能取决于实际序列长度、前缀命中、并发、TP/PCP/DCP 组合、通信带宽和内核行为。本次产物做机制与代码一致性核对，未运行硬件性能实验。评估时可同时观察 prefill 延迟、每 token 延迟、吞吐和 KV 内存，并分析通信与计算是否有效重叠。
